# Native AscendC candidates

The service accepts native source projects through the same definition/workloads
interface as Triton. The first native contract is a UTF-8 source tree, a bounded
build command, and a Python `module:function` entrypoint returning tensors. That
entrypoint can load an AscendC shared library or extension. The service does not
install a CANNBench adapter or impose its scoring policy.

## Submit a project

Create `native.json` beside the project files:

```json
{
  "kind": "native",
  "files": ["build.sh", "CMakeLists.txt", "kernels.asc", "extension.cpp", "entry.py"],
  "build": ["bash", "build.sh", "dav-2201"],
  "entrypoint": "entry:add",
  "build_timeout_seconds": 300,
  "kernel_names": ["native_add"],
  "event_timing": false
}
```

`files` in this **CLI manifest** is an explicit list relative to the manifest
folder. The CLI reads those files as data and sends their contents in the API's
`candidate.files` mapping. It never builds or imports the project locally. Source
paths must be relative POSIX paths without empty, `.` or `..` components;
symlinks and special files are rejected. At most 128 files and 2 MiB of UTF-8
source are accepted. Native project packaging requires the client's POSIX
no-follow file APIs. The manifest is not a directory glob or archive upload.

```bash
CLI=plugins/triton-eval/skills/triton-eval/scripts/triton_eval.py
python3 "$CLI" verify \
  --definition definition.json --workloads workloads.jsonl \
  --native-project path/to/native.json --save-handle handle.json

python3 "$CLI" benchmark \
  --definition definition.json --workloads workloads.jsonl \
  --native-project path/to/native.json --warmup 3 --repeats 5

python3 "$CLI" evaluate --checks compile \
  --definition definition.json --workloads workloads.jsonl \
  --native-project path/to/native.json
```

Configure `EVALUATION_URL` and `EVALUATION_CAPABILITY_FILE` as for existing
Triton requests. `--triton` and `--native-project` are mutually exclusive. Use
`--candidate-only` for native measurement without a reference comparison; its
result remains correctness-unverified. For custom inputs this flag preserves the
reference's generator source just as `--triton-only` does.

## Build and runtime

Builds run after durable admission in the leased attempt's private project
directory. Relative paths in build argv resolve there; paths used by entrypoints
should be based on `__file__`. The entrypoint module must be included in the
source tree. Binary results such as `.so` files are generated by the build.
Provide dependencies in the configured worker runtime; a build must not modify
shared Python, CANN or OPP installations.

Execution isolation follows the existing engine sandbox configuration. A private
project directory alone is not a security boundary: in host execution mode the
build has the worker user's permissions. For isolated service deployments, use
the configured sandbox with read-only runtime/toolchain mounts and private
writable build storage; validate compiler and profiler access there on the server.

The worker needs a matching CANN/AscendC compiler, headers, libraries, native
host tools and torch/torch_npu ABI. The service does not infer a compatible
compiler architecture from a file extension. Compile-only attempts have no NPU;
build commands must not require device initialization for that path.

The request/source identity includes all files and build metadata. Builds and
native method evidence are scoped to the attempt. Native baseline-cache and
correctness-evidence reuse are unsupported in this first contract; explicit
requests for them are rejected. Build failures retain bounded stdout/stderr,
exit status and duration in `result.native_build`.

## Correctness and timing

Native comparison uses the `native_tensor_v1` strict path: output trees,
shapes and dtypes must match, integer values compare exactly, and floating
results use the declared workload tolerance or the native method's defaults.
Inspect outcome and case coverage, not just the resource's terminal state.

For floating outputs the native method compares in FP64 using
`abs(candidate-reference) <= max_atol + max_rtol * abs(reference)`.
Its default `(max_atol, max_rtol)` is `(0.09, 2**-10)` for float16,
`(0.1, 2**-7)` for bfloat16, and `(0.001, 2**-13)` for float32/float64.
The default required matched ratio is 1.0. A supplied `max_error_cap` is a
direct absolute-error bound in output units for this method, not the older
declared-tolerance method's scaled cap. Supply task-appropriate overrides;
these defaults do not claim CANNBench precision compatibility. Non-compute
mode requires bit-exact output. Non-finite floats are rejected, except matched
negative infinities explicitly allowed by `allow_negative_inf`.

Native timing defaults to profiler. Its `native_profiler_kernel_sum_v1` method
warms up before capture, captures each measured call separately, sums its kernel
durations (including repeated same-name launches), and averages the call sums.
Reference and candidate use the same method. This is not CANNBench's aggregation
and does not establish leaderboard parity.

The native profiler accepts 1–100 repeats (default 20); its per-call samples
survive in `implementation_samples_ms` / `reference_samples_ms`, or
`measurement_samples_ms` for a single implementation. Joint native
performance plus trace requests are not supported in this release; submit
them separately. Artifact integrity checks reject build outputs that change
between checks. These checks do not certify a same-process judge against
malicious candidate code.

Build outputs must contain only regular files and directories (no symlinks),
within the service's bounded artifact-tree limits. Evaluation code must not
modify that tree; write scratch data outside `native_candidate`. Completed build
diagnostics are bounded tails, saved under the attempt's lease before later
checks. Published build evidence survives subsequent worker exceptions, deadline
expiry and lost-worker recovery; a replacement attempt starts with fresh evidence.
A build killed before that publication has no completed build record. Build logs
are exposed in terminal results, not as a separate streaming artifact store.

Event timing requires both `--method event` and `event_timing: true` in the
manifest. This declaration means the extension launches on the stream bracketed
by the service's timing events, or establishes the necessary stream dependencies.
It is a caller assertion, not automatic stream verification. Synchronizing the
whole device after recording the end event does not repair missing dependencies.

Native op/deep profiling needs explicit `kernel_names` for attribution;
Triton decorators are not used to discover native kernels. Trace and diagnostic
results have their own method and coverage semantics.

## Device validation

The [smoke fixture](../../tests/fixtures/native/ascendc_smoke/README.md) provides
small pointwise, reduction and matrix kernels with non-aligned sizes. Run the
HTTP gate against an isolated service with available NPU resources:

```bash
python3 scripts/npu_native_gate.py \
  --service-url "$EVALUATION_URL" \
  --capability-file "$EVALUATION_CAPABILITY_FILE" \
  --expected-hardware-model 'EXACT_WORKER_HARDWARE_MODEL' \
  --expected-runtime-version 'EXACT_WORKER_RUNTIME_VERSION' \
  --compiler-arch dav-2201 \
  --output /tmp/native-gate.json
```

The gate requires all three correct candidates, their profiler measurements, an
intentionally wrong NPU add kernel, a build failure and a runtime failure. It
saves raw evaluation resources and fixture hashes, checks actual worker
provenance and fails on missing/partial evidence. It does not calibrate timing
stability, validate all compiler versions, or replace cancellation/recovery,
profiler-attribution and broader device release tests. CPU tests do not establish
that these AscendC sources compile or execute on the target NPU.
